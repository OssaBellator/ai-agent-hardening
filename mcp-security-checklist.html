MCP Security Checklist for AI Coding Agents

Model Context Protocol servers can give coding agents access to files, APIs, databases, shells, and other high-authority tools. That makes MCP configuration part of the repository's security boundary, not just developer convenience.

Fast self-check

  1. Inventory every server and tool. Know what is connected, where it comes from, and what authority it has.
  2. Use least privilege. Give each server only the filesystem paths, network access, OAuth scopes, and credentials required for its job.
  3. Treat tool definitions as untrusted input. Review descriptions and schemas, and detect unexpected changes after approval.
  4. Treat tool output as untrusted input. A legitimate-looking response can carry prompt-injection instructions back into the model context.
  5. Separate sensitive tools. Payment, production, identity, email, secrets, and administrative actions should not sit behind the same broad authority as routine coding tools.
  6. Require confirmation for destructive or data-sharing operations. Show the actual parameters to the user rather than only an agent-generated summary.
  7. Sandbox local servers. Restrict filesystem access, network access, credentials, process authority, and persistence.
  8. Validate tool arguments server-side. Do not rely on a system prompt to enforce path, command, SQL, URL, or authorization rules.
  9. Use scoped, replaceable credentials. Prefer short-lived or task-scoped credentials and do not share one token across unrelated servers.
  10. Log actions without logging secrets. Keep enough evidence to audit tool use while redacting credentials and sensitive payloads.

Repository checks

Review agent instruction files such as AGENTS.md, CLAUDE.md, Cursor/Claude rule directories, MCP configuration, package manifests, and CI workflows together. A repository may be individually reasonable in each file while still creating excessive authority when those surfaces are combined.

Watch especially for permission-bypass flags, broad write scopes, credentials in tracked configuration, mutable/unreviewed MCP dependencies, rules that let agents modify their own persistent instructions, and CI jobs that can execute untrusted changes with privileged tokens.

GitHub Actions: keep privileged triggers isolated

GitHub documents pull_request_target as a privileged event because it can receive the base repository's token and secrets. If it is needed, do not use it to check out and execute untrusted pull-request code with those privileges. Prefer a normal pull_request workflow when secret access is unnecessary, and keep GITHUB_TOKEN permissions at the minimum required level.

Tool poisoning and rug-pull resistance

An MCP tool's name, description, parameter schema, and returned content all become part of an agent's operating context. Review these surfaces as executable influence even when they are only text. Pin or snapshot approved tool definitions where practical and investigate changes before re-authorizing a server.

What a static repository scan can and cannot prove

A static scan can inventory known configuration surfaces and flag obvious credential or authority patterns without running target code. It cannot prove that a server is benign, that a credential was never exposed elsewhere, or that an agent cannot be manipulated at runtime.
