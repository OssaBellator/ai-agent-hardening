AI Coding Agent Repository Hardening Checklist

This checklist is for repositories used with coding agents, MCP servers, automation, deployment CLIs, or other tools that can read files, execute commands, or change remote systems. It is a practical review guide, not a security certification.

1. Keep secrets out of the repository

  • Do not put API keys, passwords, private keys, recovery phrases, or long-lived tokens in tracked files.
  • Keep credential requirements separate from credential values.
  • Check generated logs, receipts, screenshots, test fixtures, and cached outputs for accidental secret material.

2. Separate read authority from write authority

  • A tool that only needs inspection should not automatically receive mutation authority.
  • Keep local workspace writes separate from remote writes such as deploys, pushes, messages, charges, or account changes.
  • Make high-impact operations explicit rather than relying on ambient shell access.

3. Bound tool inputs

  • Prefer explicit paths, enumerated modes, validated URLs, and fixed operation shapes over arbitrary command strings.
  • Constrain file operations to the intended project root.
  • Reject path traversal, unexpected protocols, and unbounded payload sizes.

4. Verify the exact thing you are about to trust

  • Bind readiness evidence to the current provider/tool version and configuration.
  • Treat changed binaries, changed configuration, rotated credentials, or expired checks as reasons to re-verify.
  • Do not equate “installed” with “authenticated,” or “authenticated” with “ready for mutation.”

5. Put irreversible actions behind a distinct gate

  • Deployments, payments, submissions, account mutations, destructive deletes, and other hard-to-reverse actions should have separate authorization.
  • Use idempotency keys or durable effect records where retries could otherwise duplicate an external action.
  • Record enough non-secret evidence to distinguish prepared work from completed external effects.

6. Make recovery independent of the current agent session

  • Assume the current chat, process, machine, or local cache can disappear.
  • Document where source, state, credentials, and recovery material are restored from.
  • Verify backup manifests or checksums before claiming a recovery path works.

7. Do not auto-resume stale work blindly

  • After restart, re-check current repository state, remote state, credentials, and outstanding external effects.
  • Use durable identifiers so a resumed process can tell whether an operation already happened.
  • Fail closed when state is ambiguous rather than fabricating success.

8. Treat test/build success as evidence, not as a universal safety proof

  • Run the repository-appropriate build, type, lint, test, and smoke checks that are actually available.
  • Record skipped or unavailable checks rather than silently treating them as green.
  • Verify important user-visible or external outcomes independently when practical.

9. Minimize what leaves the machine

  • Send only the context required for the task to remote models or services.
  • Keep private records and secret values out of general logs and public artifacts.
  • Prefer redacted metadata and references when full payloads are not required.

10. End with a usable handoff

  • List what changed, what did not change, and what still requires customer action.
  • Document credential locations without copying credential values.
  • Include recovery steps, authority boundaries, verification results, and known limitations.
